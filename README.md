# melloway

Less planning, more chemistry. A Sydney date and hangout phone app, migrated from the supplied HTML and Markdown prototypes (preserved in `prototype/`).

## Run locally

Use Node 22+ (tested on Node 24).

```sh
npm install
npm run dev
```

Open http://localhost:5173. This starts Vite and the server-only provider adapters on port 3001. Without credentials, planning uses a sourced catalog of real Sydney CBD and Newtown venues. Maple Shore headings and Outfit body text load from the supplied local files in `public/fonts/`, with no Google Fonts dependency. External mood images and street-map tiles require an internet connection; neutral placeholders preserve the rest of the flow when they fail.

```sh
npm test
npm run build
npm run preview
```

End-to-end tests are included in the repository. Install the test browser once, then run:

```sh
npm run test:e2e:setup
npm run test:e2e
```

Playwright starts and stops the local app/API automatically. If you use an installed Chrome instead, set `PLAYWRIGHT_EXECUTABLE_PATH` to its executable. The suite uses sourced catalog data, explicitly labelled legacy fixtures, mocked AI and local map tiles, without paid provider requests or requests to the public tile service. Tests cover the complete journey, swaps after reopening favourites, details and spotlight navigation, fresh drafts, save/delete persistence, community posts/likes, profile edits and icon tabs, saved/liked routes and events, empty results, and 320px/390px viewports with reduced motion. These are Chromium viewport checks, not native iPhone or WebKit tests.

Verified: production build, 45 Node planner/provider/intent tests and 43 Playwright phone-flow tests. Google provider tests use synthetic responses to check request batching, route index mapping, unavailable edges and Sydney location search/resolution; real credentials were not used. Sydney timestamp tests cover seasonal offsets and clock-change boundaries.

The production build is `dist/`. Deploy to any static host with a SPA rewrite to `index.html`. To use live Google data, also host `server/index.js` in a Node service and reverse-proxy `/api/*` to it. The static build runs independently with the sourced catalog and local preference scoring. Do not deploy the Google adapter as an unrestricted public proxy: configure authentication, an origin allowlist and shared rate limiting for production. Its current IP rate limiter is suitable for a local hackathon demo, not distributed production traffic.

## Integrations

Copy `.env.example` to `.env` and configure only the providers you have.

### OpenAI recommendations

Set `OPENAI_API_KEY` in the server-only `.env`, then restart `npm run dev`. `OPENAI_MODEL` defaults to `gpt-4.1-mini` and can be changed to a Responses API model supporting structured outputs. See [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

This works with OpenStreetMap and the sourced Sydney catalog, independently of Google. Generation first interprets semantic intent (such as a hidden, intimate bar or upscale dinner), then ranks the supplied real places. The planner chooses an activity sequence and enforces area, opening windows, total allowance, duration and travel limits. Selected chips, explicitly chosen carousel ideas and notes are prioritised in an exact first pass. If that cannot fit, the planner keeps available matches and finds related open alternatives, ranked by retained interests, activity similarity, atmosphere and proximity. A brief “Closest match” line explains substitutions. Exclusions and the chosen date/time, budget and duration remain constraints; the original answers are preserved. Swaps retain the other stops and exclude previously rejected venues. Missing credentials or provider failures use the same sourced catalog with local intent interpretation and weighted scoring. No new generated route falls back to fictional demo businesses.

Only planning details and a compact candidate list are sent to OpenAI; profile names, partner names, age, gender, photos, reviews and precise coordinates are omitted. Notes are sent as written, so personal details typed there are included. Responses use `store: false`. Generation uses up to two calls: intent (700 output tokens) and ranking (1,600), each with a 12-second timeout. Replacements and optional suggestions use ranking only. Both endpoints share six AI calls per minute per IP. Invalid outputs, rate limits and outages fall back locally. OpenAI API usage is billed separately. Automated tests mock OpenAI and never load the secret. This integration does not scrape TikTok, Instagram, Google Reviews or new businesses.

### Place previews from TikTok and Instagram

Venue pages replace missing hero images with a two-column “see the vibe” grid. With `OPENAI_API_KEY`, the server uses [Responses web search](https://developers.openai.com/api/docs/guides/tools-web-search) to find indexed public posts about the exact Sydney venue. `OPENAI_MODEL` must support web search (the default `gpt-4.1-mini` does). Only individual TikTok video and Instagram post/reel URLs present in the returned search sources or citations are accepted. Posts for similarly named places in other cities are excluded by the search instructions. Venue name, public address and venue coordinates are sent for this search; no user profile or itinerary answers are included. Responses use `store: false`. Search adds billed API usage; set server-only `OPENAI_SOCIAL_SEARCH=false` to disable it. Results are cached for six hours (empty results for 15 minutes), concurrent identical searches share one request, and discovery shares the existing six AI requests per minute limit.

[TikTok oEmbed](https://developers.tiktok.com/doc/embed-videos/) supplies real thumbnails and creator names when available. Instagram cards use the platform’s own post embed rather than substituted photos. Tapping a card opens the official player/embed with an original-post link. Private, deleted, unindexed or blocked posts may have no preview; the page keeps venue details usable and offers platform searches. This is public indexed-post discovery, not access to either platform’s full feed or private content. No social engagement counts or creator identities are invented. Users can add and remove individual public-post links; those links stay on that device, are labelled shared links, and are not verified as venue matches. Tests mock all discovery, metadata and embeds and make no paid requests.

### Google Maps Platform

Google is optional. Leave its keys blank to keep the OpenStreetMap and sourced-catalog flow.

Enable billing, Places API (New) and Routes API. Set `GOOGLE_MAPS_API_KEY` on the **server only**, restrict the key to those APIs and your server infrastructure. Never prefix it with `VITE_`. Discovery uses Text Search with geographic bias and requires known regular opening periods. Photos are fetched through a server proxy, with author names shown. Discovery failures fall back to the sourced catalog; routing failures use labelled geographic travel estimates.

The introduction’s location field uses [Places Autocomplete (New)](https://developers.google.com/maps/documentation/places/web-service/place-autocomplete) restricted to the Sydney region. Search is debounced and cancelled when the text changes; selecting a suburb, address or venue resolves its coordinates through [Place Details (New)](https://developers.google.com/maps/documentation/places/web-service/place-details) using the same session token. Those coordinates centre nearby discovery and planning within 3 km. Without credentials or when search fails, suggestions are explicitly labelled local Sydney areas. Arbitrary text must be selected from suggestions before continuing; “anywhere in Sydney is good” leaves the area open. A compact interactive map shows selectable local Sydney areas with OpenStreetMap tiles, zoom and a reset control. Map selection and local search selection update the same saved area; map pins remain usable if tiles fail to load. Google search results retain their separate provider attribution and are not plotted on third-party tiles. The API key stays on the server. `npm run dev` watches the API code for changes; restart it after configuring `.env`.

Live Places ratings and photos are provider-supplied. Prices and visit lengths remain labelled planning allowances. Regular hours do not guarantee holiday opening, reservations or event availability. Transit matrices are batched to stay within Google’s element limits and use the selected Sydney date/start time (including daylight saving). These are initial route estimates: later legs may have different departures, and future timetables can change. Walking/driving matrices use request-time routing. Confirm your actual outing route in Google Maps. Review Google Maps Platform attribution, storage and terms before a public launch; saved plans currently store venue snapshots for demonstration.

Directions always open Google Maps. For live Google Places results, optionally set a **separate public** `VITE_GOOGLE_MAPS_EMBED_KEY`, enable Maps Embed API, and restrict that key to the Embed API and your app’s HTTP referrers. This enables an embedded Google directions map with the selected stops and transport mode; without it, the route area links to Google Maps. The server’s discovery key is never copied into the client. See [Maps Embed documentation](https://developers.google.com/maps/documentation/embed/embedding-map). Google Places results are never plotted on non-Google tiles.

Curated plans and legacy demo routes use Leaflet and OpenStreetMap street tiles. The pink dotted line shows stop order with straight connections, not a calculated road route. Curated positions are approximate address positions; legacy demo coordinates remain sample locations. Nearby pins group their numbers so none are hidden and separate on zoom. The map preview leaves page scrolling available; “expand” opens a native full-screen dialog with pan, pinch zoom, keyboard controls, the stop list and directions. Escape or close restores focus and page scrolling. Tile failures keep the plan, details and save controls usable. Attribution remains visible beneath the map controls. Tile requests use browser caching and only fetch the visible area. `VITE_MAP_TILE_URL`, `VITE_MAP_TILE_ATTRIBUTION` and `VITE_MAP_TILE_ATTRIBUTION_URL` allow replacing the tile provider together. See [OpenStreetMap’s tile policy](https://operations.osmfoundation.org/policies/tiles/).

### Supabase

Set browser-safe `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`. Run `server/schema.sql` in Supabase’s SQL editor and enable anonymous sign-ins. Row-level security ensures users access only their own itineraries. Never expose a service-role key. Favourites save locally first, with cloud sync when configured; sync failures are surfaced. Anonymous cloud ownership stays tied to that browser session; this MVP does not implement cross-device accounts. Configure CAPTCHA and sign-in rate limits before public use.

## Planner

The recommendation engine lives in `src/engine/`: semantic preferences, eligibility filtering, scoring, activity sequencing, route generation and replacement. A bounded search considers at most 14 candidates across cohesive templates, such as café → shop → bookshop, gallery → walk → meal, or bar → upscale dinner → bar. Shorter routes are allowed when they fit better. Exact date/start, published opening windows, total budget and outing duration constrain every route. An untouched 11 am default may become 6 pm for dinner/cocktail intent; a chosen time always wins and inferred times are disclosed. Walking legs are limited to 2.5 km / 45 estimated minutes, other modes to 4 km / 35 minutes, unless notes explicitly allow longer travel. This is a bounded search, not global optimality. Google graph edges use Routes; OpenStreetMap supplies map tiles, while local travel times use geographic estimates. Driving includes a $15/person allowance; transit includes $10/person, neither a live fare.

`recommendationWeights` in `src/engine/scoring.js` configures preference (26), atmosphere (18), proximity (18), budget (10), evidence quality (6), variety (8) and timing (14). AI fit blends with local venue scores; ratings contribute only a small optional component. The scheduler checks feasibility independently of AI scores. Each chosen stop includes a brief reason in its details. Replacements match the stop's activity role, preserve the other venues and reasons, reschedule the whole plan, and persist rejected IDs. When an exact route cannot fit, `src/engine/alternatives.js` tries related activity templates and shorter routes, including a single useful stop. It uses the same sourced venue facts and scheduler, and makes no additional OpenAI call. Unknown hours, known closures, explicit opt-outs (including “no bars”) and rejected venue IDs remain excluded. If no open, sourced option can fit at all, an explanation offers a time or area change.

`src/data/sydneyVenues.js` contains 21 real CBD/Newtown/Glebe places with linked sources checked 11 October 2026, addresses, approximate coordinates, activity roles, editorial atmosphere tags, spending/visit allowances and published hours. It supports romantic evenings, matcha/shopping and affordable art/walks. Unknown closing times are excluded from automatic planning (for example Hubert's “late” closing); known holiday closures and the garden's seasonal hours are applied. Glebe Markets are only scheduled on Saturdays. Maeda's matcha availability is reported by a secondary source and explicitly unconfirmed; Saturday Mapo hours are omitted because the operator's published wording is ambiguous. Venue menus, holiday changes, reservations and dietary/accessibility requirements still need confirmation. No photos, ratings or reviews are fabricated; unavailable photography uses the existing placeholder. Browsing shops uses a $0 allowance with purchases extra. Café food/brunch requests use a meal allowance rather than a drink-only allowance. Unsupported activities try the closest available related option; areas with no feasible sourced venues still return a coverage message. Linked sources and limitations remain in place details; optional additions use this same catalog without inventing a photobooth.

## Screens and storage

Landing → name → age/gender → hanging out/location/budget → illustrated date idea → free-text notes → processing → a compact outlined route card with editable place/address rows, an inset map and a nearby suggestions grid. Place arrows and map pins open venue details; suggestion previews keep additions opt-in. Larger venue cards live under the optional “stop details” section, and time/cost totals expand below the map. Date, time and transport remain available within the hanging-out screen; multiselect interests are available beneath the suggestion carousel. Suggestions and recognised interests from notes contribute to planning. Notes remain attached to results; unrecognised requests, dietary requirements and bookings are not verified. Details expand, venues have spotlight pages, plans regenerate, directions open externally, and favourites persist across reloads. Reopened saved plans can swap a single stop directly: replacement candidates are reloaded on demand while preserving the rest of the plan. Starting a new plan clears the draft while keeping favourites. Explore is a compact community feed with avatars, names, @handles, short route stories and horizontally scrollable stop-photo strips. The header contains only a profile icon, an always-visible search field and an “m” home mark. Posts use rounded black-outlined cards with route photos, one full-route link and reply/like/save actions; route totals appear inside the expanded route. Reply threads, likes, route bookmarks and search work locally and survive reloads. Your Posts and Likes filters are available through the profile’s icon tabs. “Check full route” and individual stop photos open a dedicated community route page with the original post, photo strip, simple lettered place/address rows, map and an Explore-style grid of other route posts. Place arrows, photos and map pins open a venue details sheet; suggested tiles open their own complete post. Browsing preserves the user's current outing; “make this my day” creates an editable personal copy. The expanded post heart saves/removes the shared route. Venue spotlights return to the expanded post. The composer attaches the current or a saved plan and accepts an optional memory photo. Starter profiles/routes are fictional and all demo photographs are mood imagery; the six existing starter-post photos are bundled locally, with sources in `public/images/community/SOURCES.txt`, so those cards also load offline; there is no public social backend yet. Maps load only in the expanded route, keeping the feed lightweight. What’s On uses tall original SVG event posters, organiser names and @handles, expandable details, search/category/liked/saved filters, and persistent local likes and bookmarks. Saved has separate routes/events tabs; saved posters reopen their own details. Planning around a poster adds its area and interests to the introduction. Event dates, times, venues and entry prices remain explicitly unconfirmed sample data. There is no public social backend or live events provider yet.

The `/profile` screen uses an inset rounded cover, overlapping avatar, compact name/@handle/bio and the same outlined post cards as Explore, with icon-only Posts, Saved and Likes tabs. The cover pencil opens a full-screen editor with an editable cover, overlapping avatar camera, compact label/value rows and bottom cancel/save buttons; a plus beside the avatar opens the post composer. Open it from the avatar in Explore or the secondary-page header, or from the introduction menu. Name, @handle, bio, location, optional birthdate and TikTok/Instagram URLs, cover colour and optional JPEG/PNG/WebP avatar and cover photos (up to 1 MB each) are editable and persist locally; edits also update the identity displayed on your own posts and expanded routes. Saved includes existing routes and event posters; Likes includes community posts and events, with working remove/open actions. The tabs support arrow keys, Home and End. This is a device-local profile, not an authenticated public account; there is no password, cross-device profile sync or public publishing yet. Personal profile answers stay in browser storage; no sign-up is required. No profile demographics influence recommendations. Clear browser storage to remove drafts and demo posts; remove favourites in the app. Profile, itinerary, local community and cloud storage are separate concerns.

## Phone app

The interface uses a phone-sized shell (up to 480px), including desktop previews. The introduction follows the supplied wireframe image: a centred Maple Shore logo and start button, separate conversational questions, floating doodles, an original illustrated suggestion carousel, a notes screen, simple loading, and a large expandable map above a rounded sheet with photo venue cards and bottom navigation. Outfit is used for body text and controls. Black and white carry the interface. Pink, yellow and green are reserved for small original illustrations and intermittent background doodles: an apple, matcha cup, flower, camera, sparkle and leaf, distributed across six background positions. Three motifs remain softly visible while three appear intermittently; all use gentle fades and drifts, remain behind content, and cannot intercept touches. They stop moving for reduced motion, hide while the keyboard is open, and pause when the page is hidden.

Motion uses short screen exits/entrances, short preset typewriter prompts, one active question at a time within the original screens, immediate chip feedback, touch-friendly carousel navigation, stage messages driven by actual discovery work, and local stop transitions. Age uses a wide number field with a numeric keyboard. Budget uses the same roomy field with a decimal keyboard, a dollar prefix and an AUD-per-person label; free/$40/$80/$120 shortcuts fill it in one tap. Custom amounts and cents persist, and blank or out-of-range values must be corrected before continuing or opening extra details. The total is split into food, drinks, shopping and activities after reserving transport. Venue estimates remain separate from spending allowances: free browsing gets a purchase allowance, weighted toward shopping rather than books, with a buffer left for extras. Expand the trip totals to edit category budgets; blank fields use automatic allowances and reset restores the automatic split. Custom category budgets constrain generation, alternatives, swaps and additions, including money reserved for a category with no current stops. Adding an extra cannot silently reduce an existing shopping allowance. Edits, saved plans and reloads preserve the split, and totals include purchase money. Changing the onboarding total or transport resets category budgets to automatic. Continue moves from age to gender, then company, occasion, location and budget. Food preferences are asked in the main flow, followed by a separate optional dining vibe question. Cuisine chips guide food stops; Chill, Cozy, Lively, Outdoors and Fancy softly rank dining atmospheres without requiring extra stops or changing the chosen time. Both answers persist and can be skipped. Optional day/time/transport details and other interest groups are also answered individually. An inline month calendar supports today/tomorrow shortcuts, past-day disabling and keyboard navigation. Time has morning/afternoon/evening shortcuts and hour/minute/am-pm selectors. Date and time can be cleared with “not sure yet” or skipped independently; blank answers stay blank across reloads, and generation uses today in Sydney with an 11 am default or a disclosed intent-based evening time. Every onboarding question uses the same top and left text anchor, including the calendar and idea screen. Back returns to the previous visited question across sections and optional branches; reload preserves that trail, the current question and saved answers. Typing reserves the full prompt layout, finishes on input focus, and does not block answering or skipping. Returning with a saved name shows the complete script. Reduced motion removes movement, typing and staggering while keeping all six doodles static. Opening results shows an editable stop summary above the route map, followed by a rounded sheet of venue cards. Edit enables changing a chosen spot, moving it up/down, and removing it; at least one stop is retained. An add-stop picker searches the nearby candidate pool. Every edit reschedules the exact chosen order against opening hours, travel, outing duration and the full budget; infeasible changes preserve the existing plan. Totals, map labels, external directions and persisted plans update together, including one- and two-stop routes. Stop and suggestion headings use the place name; repeated categories and filler captions are removed. Intro prompts and page headings use concise copy, while costs, timings, addresses and source disclosures remain available; demo placeholders use plain type/area labels. Known old demo nicknames are migrated on loading current, saved and shared plans, preserving coordinates, times, prices and real Google/custom venue names. Below the venue cards, optional photobooth/dessert/walk/bookshop suggestions show their allowance and added outing time. Adding one tries feasible insertion positions while preserving the order of the main stops. Extras never enter the route without a tap. Suggestions use sourced venues or Google Places; no synthetic photobooth is added when one cannot be sourced. Search and category filters narrow the displayed cards while preserving the complete route, stop order and budget. Tapping a map tag selects its card; each card can highlight its stop on the map. The sheet handle scrolls between the map and cards. Tapping a summary stop or a card’s “the details” opens a native bottom-sheet dialog with timing, allowance and venue information. Escape and the close control dismiss it and return focus. Individual swaps remain available on collapsed cards. A lock-in button saves the plan, and a community link opens more ideas. Replacing one stop preserves the other stop components. The footer “m” opens saved plans, community and events through a native dialog; the result and secondary screens have bottom tabs, with “ur day” returning to the current itinerary. Keyboard opening keeps the introduction scrollable. Submit finishes the introduction, generates the outing, and navigates to the itinerary. Unexpected interruptions offer a retry that preserves the answers; impossible budgets/hours still require changing the details.

Safe-area spacing, native mobile form controls, accessible labels and chip states, 44px interaction targets, responsive navigation, and reduced-motion handling. Plan, replacement and community IDs remain valid UUID v4 on HTTP local-network previews, using `crypto.getRandomValues` when `crypto.randomUUID` is unavailable. The submit transition was also verified against the local-network origin, not only localhost. `capacitor.config.json` prepares the web build for Capacitor. No native iOS project was created. Add `@capacitor/ios` and run Capacitor on a configured macOS/Xcode environment when ready; Set `VITE_API_BASE_URL` to your HTTPS backend origin when packaged for iOS. Set the backend’s `APP_ORIGINS` to the exact Capacitor origins you use (typically `capacitor://localhost` on iOS and `http://localhost` on Android). The server uses an explicit CORS allowlist for those requests; no Google secret goes into the phone build.

## Structure

- `src/components`: shared controls, layout, expandable route map
- `src/pages`: app screens
- `src/hooks`: draft, current plan and favourites state
- `src/data`: sourced Sydney venues, legacy demo fixtures, preference taxonomy
- `src/engine`: intent, filtering, weighted scoring, sequencing, generation and replacement
- `src/services`: discovery, Google fallback orchestration, storage
- `src/utils`: selection, graph search, scheduling, directions
- `server`: server-only OpenAI and Google adapters, Supabase SQL
- `tests`: meaningful planner constraint and replacement tests
